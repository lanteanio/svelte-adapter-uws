## Prerequisites and supported tuples

Before editing source, keep the stable lockfile and a deployable artifact for
the currently routed release. The adapter and both sibling packages require
Node 22 or newer on both the stable and prerelease lines. A native-runtime
deployment must also use the uWebSockets.js revision from the same compatibility
row as its adapter.

Two install-time changes on the 0.6 line: the optional native addon is
verified at install (a failed uWebSockets.js install now fails `npm install`
with the loader cause instead of surfacing at first build; client-only
consumers set `SVELTE_ADAPTER_UWS_SKIP_NATIVE_CHECK=1`, and the
`svelte-adapter-uws-preflight` bin runs the same diagnosis on demand), and the
addon installs from the GitHub release tarball over HTTPS rather than the 0.5
git ref - adjust registry mirrors or egress allowlists that pinned the git
source.

| Purpose | Adapter | Realtime | Extensions | Native addon |
|---|---|---|---|---|
| Rollback baseline | exact `0.5.8` | `0.5.x` | `0.5.x` | `v20.67.0` |
| Upgrade candidate | exact `0.6.0-next.*` selected by the manifest | matching `0.6.0-next` | matching `0.6.0-next` | `v20.69.0` |

The generated [compatibility table](../../README.md#version-compatibility) is
the authority for the exact current prerelease identity. Do not copy the
wildcard in this explanatory table into a lockfile, and do not combine cells
from different rows. Inventory every adapter option, WebSocket hook, presence
or cursor selector, clustered publish, replay backend, and stored protocol
offset before changing the tuple.

## Required source edits

No existing adapter package subpath was renamed for 0.6: the root, client,
Vite, testing, and 0.5 plugin imports remain available. New subpaths are
additive. Applications still need to make these behavior choices explicit:

1. Add an allowlisting `select` callback to every presence and cursor tracker
   that must expose display fields. Do not reconstruct the old whole-user-data
   default. When adding `clientUpdateFields`, list every durable field that
   changes after join - the browser-writable ones AND the ones the server
   itself sets through `update()`, because once configured the allowlist gates
   direct server calls too.
2. For each multi-worker publish, pass `{ seq: false }` for volatile data or
   obtain a positive sequence from one external authority and publish its
   fan-out with `{ seq, relay: false }`. Apply the same policy to scoped,
   batched, and wire publishing helpers.
3. Keep the built-in game lane on one I/O worker. A multi-I/O-worker design
   needs an external room sequencer and fan-out instead of a configuration
   switch.
4. Set `maxPayloadLength` explicitly if development and production are meant
   to use a ceiling other than the reported adapter value.
5. Add an explicit `path` to every `cookies.set()` and `cookies.delete()` call
   in the WebSocket `authenticate` hook. The 0.6 API rejects a missing path.
6. If a framework grants topics server-side while the application also exports
   `subscribe` or `subscribeBatch`, use
   `authorizeWireSubscribe: 'strict'` on production and Vite, or require
   `platform.authorizeWireSubscribe('strict') === 'strict'` at startup. The
   legacy boolean policy still lets an application hook replace the grant
   check; strict requires both authorities. `svelte-realtime` requests strict
   automatically and now fails startup against an adapter that cannot confirm
   it, unless the application explicitly opts out there.
7. For handlers that can await or perform CPU-heavy work, set
   `websocket.messageAdmission` from measured per-worker capacity. The new gate
   can bound per-connection/global rate and concurrency across the app
   `message` hook, binary `0x03` ingress, and JSON `game` publishing; retain at
   most `maxQueue` waiting payloads; and answer shed frames with
   `message-overloaded`. It is additive and disabled when all limits are zero;
   do not enable automatic retries for non-idempotent messages.

Canonical diagnostics require no application source edit. Collectors should
route on the stable `source`, `component`, `event`, and `severity`
fields and treat `message` as package-owned fallback prose. Dashboards that
display decoded external `attributes` must escape them for HTML and apply
bidirectional isolation.

Distributed tracing requires no source edit unless you opt in. To enable it,
set the top-level adapter `tracing` option to a server module path whose
default or named `tracing` export implements the vendor-neutral
`startSpan(name, options)` contract. The adapter bundles that module, validates
W3C `traceparent` / `tracestate` at ingress, and exposes the active context
through `platform.traceContext` and `platform.trace`. Provider SDK/exporter
initialization remains application-owned. A configured module without
`startSpan` fails generated-server startup. With the option omitted, tracing
creates no spans and existing request behavior is unchanged.

The source checkout contains a locked 0.5.8 mini-project that applies the
projection and sequence edits, installs the locally packed 0.6 candidate into
a disposable consumer without a registry fallback, boots the consumer's own
server entry against the installed candidate, and reads the result off a real
WebSocket client - the sequence edit as a seq-less envelope, the projection
edit as fields that never reach the wire. The wire half needs the optional
native runtime and skips VISIBLY without it (CI requires it), so a quiet pass
never means it silently did not run:

```bash
npm test -- test/migration-rehearsal.test.js
```

That rehearsal is part of the normal suite and therefore runs in CI. It is a
package-boundary canary, not evidence that an application's own hooks, storage,
or sibling-package integrations were migrated.

## Default changes

| Surface | 0.5.8 behavior | 0.6 behavior | Required decision |
|---|---|---|---|
| Presence projection without `select` | Recursively projected non-sensitive user data | Only the configured safe scalar dedup key | Add an explicit public-field allowlist when clients need more than the key |
| Cursor projection without `select` | Projected user metadata | Only the connection's own safe scalar `id` | Add an explicit public-field allowlist when peers need display metadata |
| Client `presence-update` durable fields | Accepted fields without an application allowlist | Accepts none unless `clientUpdateFields` names them | Name the minimum browser-writable fields or keep server-owned updates |
| Static dotfile serving | Indexed and served every file copied out of `static/`, dotfiles included | Dot-segment paths are excluded from the index and respond 404; a top-level `.well-known/` keeps serving its own non-dot files | Rename an intentionally served dotfile or set `staticDotfiles: true`; the build warning names each refused path once |
| Vite inbound frame ceiling | Inherited the much larger `ws` default | Enforces the adapter's reported ceiling | Pin one deliberate value and test code 1009 in dev and production |
| Multi-worker implicit sequencing | Could create divergent per-worker counters | Refused at the publish boundary | Choose volatile delivery or one external sequence authority |
| Multi-I/O-worker game lane | Could fan out only on one worker | Refused at startup/use | Keep one socket worker or replace the lane |
| Distributed trace context | No native operation propagation | Optional W3C propagation through adapter, realtime, bus, webhook, and durable-work seams | Leave `tracing` unset, or deploy one provider and a coordinated ecosystem tuple |
| Established application-message admission | Cooperative client lease only; generic sends could accumulate async work | Optional server-enforced rate/concurrency gate with a bounded queue and typed shed response | Size limits from load tests; leave disabled only when the application owns an equivalent gate |
| Per-topic sequence registry cardinality | Grew unbounded for the worker lifetime; one-shot warning at a million topics | Bounded at the same threshold: subscriber-free, resume-free topics are evicted, and the carried floor means a re-published topic never repeats a sequence a client already saw | Keep the default, size `maxTopicSeqEntries` to the working topic set, or publish ephemeral high-cardinality families with `seq: false` |

## Wire and storage compatibility

The adapter owns no durable database schema, so there is no adapter database
migration to run. Its presence, cursor, subscription, and in-memory sequence
state is process-local and is rebuilt after restart. Redis, replay, CRDT, or
application records belong to the extension or application that created them;
follow that owner's versioned guide and snapshot them before its step.

The coordinated extensions release adds nullable W3C trace-context fields to
its Postgres job/task rows using idempotent schema initialization. Existing rows
remain valid with no context. Upgrade the three-package tuple in the documented
order before relying on trace continuity across Redis/Postgres or durable-work
boundaries; an older consumer safely behaves as an untraced hop.

Wire payloads do change when implicit projection is removed, and client
`presence-update` fields can now be discarded by policy. Clustered sequence
validation also rejects configurations that previously emitted ambiguous
ordering. Treat those as compatibility changes even though the JSON envelope
and existing import paths remain recognizable. Capability-negotiated binary
codecs keep their JSON fallback, but that is not permission to run a mixed
ecosystem tuple: exercise reconnect, snapshot, replay-gap, and slow-consumer
paths against the exact candidate artifacts.

## Critical policy changes

### Presence and cursor projection now fail closed

Without an explicit `select`, presence publishes only its configured key and
cursor publishes only an own `id`; either value must be a string or finite
number. Names, avatars, roles, colors, and profile fields are no longer inferred
from `userData`. Add an explicit selector containing only fields safe to expose.

Client-originated `presence-update` frames also accept no durable fields unless
`clientUpdateFields` names them. Server-side `presence.update()` keeps only the
reserved-name guard while `clientUpdateFields` is unset; once the option is
configured, the same allowlist gates direct server calls too, so list every
field the server itself updates, not only the browser-writable ones.

## Required runtime choices

### Multi-worker publishes need one sequence authority

A runtime with multiple workers refuses implicit per-worker topic counters and
numeric sequences sent through the built-in multi-origin relay. For volatile
events pass `{ seq: false }`. For recoverable events, allocate a positive
sequence in one externally ordered source and publish from that source's fan-out
on every process with `{ seq, relay: false }`.

Apply the same choice to `publishWire`, scoped topic methods, and every
`platform.batch()` or `publishBatched()` entry. A wire batch that needs replay
ordering puts the authoritative number on each entry - `{ data, seq }`, the
per-entry form described next.

`publishWireBatch` is stricter about the OPTIONS object, and the rule is
**not** limited to multi-worker runtimes. One options object cannot carry
one-seq-per-entry: a numeric batch-level `seq` would give every entry the same
number whatever the topology - and a client that received only part of the
batch then reports that number as its watermark, after which the resume floor
discards the rest. A numeric `options.seq` is therefore refused on this
surface outright: on a single worker too, in the Vite dev plugin and
`createTestServer` (which previously accepted it and produced the same
corruption), and whatever the entries array holds - twenty entries, one, or
none. The check runs before the array is inspected, so the contract cannot
appear to hold while a tick happens to produce a single update and then start
throwing when it produces two.

The authoritative number belongs on the ENTRY: each entry may carry its own
`seq` - `{ data, seq }`, a positive integer, validated for the whole batch
before anything is stamped or delivered - with exactly
`publishWire({ seq: N })`'s semantics: stamped verbatim, never advancing the
counter, recorded through the monotone-max guard. Only a NUMBER is an
explicit entry seq; any other spelling falls through to the shared options,
exactly as it would on `publishWire`'s own options object, and entries
without one draw from the shared options as before. On a multi-worker runtime the clustered
spelling is `{ seq: false, relay: false }` on the options plus a seq on each
entry: options renounce the counter, entries carry the authority, and
`relay: false` proves the built-in multi-origin relay is not also fanning out
- the same proof `publishWire` demands for the same reason.

The declaration says all of this too: `publishWireBatch`'s `options.seq`
narrowed from `boolean | number` to `boolean`, and its entries widened to
`{ data, excludeWs?, seq? }`. TypeScript callers who passed a batch-level
number get a compile error where they previously got a clean build and a throw
on the first tick that reached the call. The number-accepting siblings -
`publish`, `publishWire`, `publishBatched` and the scoped topic methods - are
unchanged.

No action, but the batch one-read guarantee is worth checking against what you
relied on, and the two batch surfaces no longer promise the same thing.
`publishWireBatch` reads the WHOLE array - every entry's `data`, `excludeWs`
and `seq` - before it builds the first envelope, which is where a payload's
`toJSON` first runs. Application code inside the call therefore cannot change
what that call publishes, in either direction: not an entry already built, and
not one whose turn has yet to come. `sendWireBatch` keeps the narrower rule of
reading each entry once when it reaches it, so a `toJSON` there can still
change a later entry, which is delivered as it reads when its turn comes.
Neither freezes a payload's own fields - every path holds the same object - so
do not mutate a payload from inside one that has been handed to a publish.

The bundled plugins need no action: cursor, presence, and groups declare
`{ seq: false }` on their own broadcasts (their state is re-established by
snapshot, not by replaying missed frames), and the in-memory replay buffer
refuses to be created in a multi-worker runtime because its history and
counter are per-worker - use the shared-backend replay from
`svelte-adapter-uws-extensions` there, or run a single worker.

One configuration does need a look, because "re-established by snapshot" is
only true mid-session while the roster heartbeat runs. If you pass
`heartbeat: 0` to `createPresence`, the constructor now warns once: with no
heartbeat, nothing refreshes a client's `maxAge` window and nothing re-adds an
entry its sweep removed, so a client on the default 90 s sweep empties its
roster roughly 135 s after the last diff even when no frame was dropped. Pass
`maxAge: 0` to `presence()` on the client to complete the opt-out, or set a
heartbeat below a third of the client `maxAge`.

### The game lane is single-home

The built-in game relay owns its room sequence and sender-excluding fan-out on
the socket worker. It is valid with one I/O worker, including clusters whose
other workers are compute-only - but `grantPublish` and `publishGame` must run
on that I/O worker: a compute worker owns no sockets, so calling the game lane
there is refused rather than sequencing rooms nobody receives. More than one
I/O worker is likewise rejected rather than delivering to only one worker.
Keep the game lane on the single I/O worker or move sequencing and fan-out to
an external authority.

## Observable behavior changes

### Authenticate cookies match SvelteKit's protective defaults

The WebSocket `authenticate` cookie API now requires `path` and defaults to
`HttpOnly`, `SameSite=Lax`, and `Secure`. As in SvelteKit, `Secure` defaults to
false only for plain HTTP on `localhost`; the production and Vite paths derive
that decision from the actual request URL, and a relative `path` is resolved
against that URL before serialization. Pass `httpOnly: false`,
`sameSite: false`, or `secure: false` explicitly only for a deliberately weaker
cookie. Existing setters without `path` now throw and must be updated before
promotion.

### Cursor smoothing honors reduced-motion preferences

Cursor canvas interpolation pauses automatically while the browser matches
`prefers-reduced-motion: reduce`, painting only discrete wire changes, and
resumes live if the preference changes. No source edit is required; visual
tests that assert interpolated motion should force the no-preference state.

### Dev and production enforce the same inbound payload ceiling

The Vite WebSocket receiver now enforces the adapter's reported payload limit
instead of inheriting the much larger `ws` default. A frame over the limit
closes with code 1009. Set `maxPayloadLength` explicitly when development needs
a different ceiling; do not rely on the old discrepancy.

### Native backpressure drops are exact telemetry

`platform.pressure.droppedFrames` and `.droppedBytes` report the last sample
window, while the corresponding cumulative metrics retain exact uWS drop
events. The bounded connection walk remains queue-headroom telemetry and must
not be interpreted as loss.

### Adapter-owned 500s echo their request id

SSR, WebSocket authentication, and WebSocket upgrade-hook failures now include
the resolved correlation id in their canonical server diagnostic and echo it
as `X-Request-ID` on the adapter-owned `500` response. Application responses
remain unchanged: set the header explicitly when successful or app-owned
responses should expose it. No source edit is required unless a proxy or test
previously assumed that adapter error responses never carried this header.

### Structured diagnostic prefixes are package-attributed

Structured adapter, extensions, and realtime lines now start with
`[lantean/diagnostic source=... component=... event=... severity=...]`.
If a collector split `[adapter-uws/assert]`, `[extensions/fatal]`,
`[realtime/assert]`, `[ws]`, `[tls]`, or `[svelte-realtime]` directly, switch
it to `parseDiagnostic()` from `svelte-adapter-uws/observability` and route on
the returned record fields. The parser accepts the explicitly inventoried old
families during the 0.6 compatibility window and marks them `format: 'legacy'`.
Assertions and migrated operational events emit the canonical grammar; every
intentionally retained warning/error site must begin with a parser-covered
legacy family. Each package enforces that bounded inventory with
`scripts/check-diagnostic-attribution.js`, wired into `npm run check`. Unknown
or malformed lines return `null`.

### Operational failures share one process sink

The adapter observability entry point now exports
`setOperationalEventSink(sink)` and `emitOperationalEvent(input)`.
Configuring the sink once also captures participating extensions and realtime
events in that process. Existing applications require no code change: the
default remains a canonical one-line JSON console diagnostic. Applications
that previously depended on a realtime `onError` callback as the only
production record should move logging to the operational sink and retain
`onError` only for application-specific observation. A sink that throws or
rejects fails over to console together with an `operational.sink.failed`
record, so collector failure cannot erase the original event.

### Default pressure logs omit raw topic identifiers

The topic-cardinality and runaway-publisher console diagnostics now expose a
process-local keyed topic reference and size metadata, not the topic string.
This is a privacy-hardening default: log searches that matched a literal topic
must switch to the opaque reference during one worker lifetime.

Applications that deliberately need the raw value can register
`platform.onPublishRate(callback)`. That callback already suppresses the
default warning and receives the raw event list, making the application's
observability sink and retention policy the explicit trust boundary.

### Divergence detail moves behind opaque ids and admin authorization

Cross-worker state mismatch logs no longer contain epochs, hashes, thread
groups, or topic-adjacent detail. They emit one opaque `diagnosticId`. The
aggregate detector is unchanged; after a mismatch, workers collect a bounded
second-stage sequence summary under process-lifetime HMAC stream ids. Operators
using `svelte-realtime` can resolve the exact record at
`GET <adminPath>/diagnostics/<diagnosticId>` after the configured mandatory
admin authorization gate. Raw topic names are absent from that response too.

No application source edit is required for detection. Update log parsers and
runbooks that expected `majorityHash` or `minority` fields on the console line,
and make sure the authenticated admin handler is configured before depending on
detail lookup. Custom admin integrations may call `platform.diagnostic(id)`
only after their own authorization boundary; never expose it publicly. Records
and per-worker stream summaries are bounded and expire as newer incidents arrive.

### Failure text is diagnostic, not localized UI

The client `failure` store now exposes `diagnosticReason` for external HTTP
status text, browser WebSocket close text, and adapter fallback text. The old
`reason` property remains as a deprecated, byte-identical alias during the 0.6
compatibility window. Do not render either field directly. Map the stable
`class`, `kind`, `code`, and `status` fields to application-owned message keys
instead; this avoids leaking browser or intermediary English into localized UI.

## Additive integration surfaces

- `upgradeAdmission.maxConnections` adds a finite per-worker ceiling for
  reserved upgrades plus live WebSocket sockets. The permit is acquired before
  per-request upgrade work and held until the socket closes; crossed attempts
  receive `503`, the waiting room observes the same capacity, and
  `ws_connection_headroom` reports remaining permits when metrics are enabled.
  Existing `maxConcurrent` settings retain their handshake-only meaning and
  do not bound established sockets. No migration is required for compatibility:
  `maxConnections` is `0`/unlimited by default. Deployments that need a hard
  socket/file-descriptor or aggregate connection-memory bound should set a
  finite safe integer per I/O worker and multiply by worker count when sizing
  the process-wide envelope.
- `upgradeAdmission.perTickBudget` now has a finite deferred-work boundary.
  When pacing is enabled, `maxDeferred` defaults to `1024` callbacks per
  worker; attempts beyond the current tick budget and that queue receive
  `503 Service Unavailable` instead of growing retained memory. Set an
  explicit non-negative safe integer from the burst/recovery envelope, or
  `maxDeferred: 0` to queue nothing. Dashboards can distinguish this shed
  from other capacity gates through
  `upgrade_rejected_total{reason="deferred_overflow"}` and the dedicated
  deferred depth, oldest-age, and rejection signals. Applications that enable
  pacing but relied on every burst eventually opening should size this new
  finite queue or handle the documented retry response.
- `upgradeAdmission.waitingRoom` accepts optional `appName`, `statusUrl`,
  `supportUrl`, and `incidentId` fields for the built-in holding page. They
  are trimmed and escaped; both `statusUrl` and `supportUrl` render a link
  only for a relative URL or the `http`, `https`, `mailto` and `tel`
  schemes; and the
  neutral page now follows light/dark preference through semantic
  `--waiting-room-*` custom properties. Existing configurations need no
  change unless they supply a custom page. A custom `template` now has one
  parsed `AccessibleWaitingDocument` baseline: doctype, `html[lang]` and
  `html[dir]`, non-empty title and body, exposed main landmark and
  status live region, and an exposed enabled named recovery control or safe link.
  A template that fails the baseline fails the build. The literal-brace escape
  is the single atomic form `{{{{token}}}}` for a literal token; runs of
  closing braces (nested CSS, minified scripts) pass through unchanged, and
  any other `{{` is a template error.
  Applications that need request-localized output can instead point `renderer`
  at a server module returning the same document contract plus `lang`, `dir`, and
  optional headers. Localized responses carry `Content-Language` and
  `Vary: Accept-Language`; `renderer` and `template` cannot be
  combined. With `waitingRoom: false`, HTML navigations receive a minimal
  accessible `503`; WebSocket and non-HTML clients keep the bare text body.
  A browser navigation to the WebSocket path itself now receives the same
  negotiated response for every enabled admission ceiling, including
  `perTickBudget`, instead of falling through to SSR. Every refused lane -
  waiting room on or off, cursor lane included - carries a jittered
  `Retry-After` drawn over a band of at least two whole seconds, so
  refusals are never answered one constant second; no action, the header
  is additive and the refusal bodies are unchanged.
- `svelte-adapter-uws/connection` exposes `connectionSessionId(ws)` without
  importing test helpers or exposing adapter storage symbols.
- The handler module may export `attribution(user)`: resolved once per
  connection at open over the server-trusted userData, validated
  (`tenantId` / `principalId` / `entitlement`, each `[a-zA-Z0-9_-]` and at
  most 64 chars), frozen, and readable via `attribution(ws)` from
  `svelte-adapter-uws/connection`. The bundled ratelimit plugin reads the
  attributed tenant id when its own `tenant` resolver is unset and adds
  `budget: 'principal' | 'tenant'`; `messageAdmission` adds
  `perConnectionBytesRate` / `globalBytesRate`; `docs/tenancy.md` states
  which layer owns each abuse surface's namespace and budget. No action for
  existing applications: without the export and the new options every path
  is byte-identical, and the resolver is fail-closed only where it is used
  (an invalid or throwing resolver refuses that connection at open with
  close `1008` and one `ADAPTER-ERR-ATTRIBUTION` line).
- `platform.metrics` and `platform.metricsSnapshot()` answer under `vite dev`
  when `websocket.metrics` names a module, instead of always `null`. No
  action: a dev route that branched on `null` keeps working, and dev still
  registers no adapter instruments, so the document it produces is the valid
  single-worker frame with no adapter series in it. The snapshot covers the
  adapter's own metrics and never an app's, in dev exactly as in production;
  read your own series from `platform.metrics`, which is the same live
  registry object the build bundles.
- One new stable error id, `ADAPTER-ERR-EGRESS-EVICTED`, reporting that the
  publish-egress ledger dropped a usage window that was still counting. No
  action: it fires only where `websocket.egress` ceilings are configured and
  the deployment publishes to more distinct topics or tenants inside one
  window than the ledger holds, and it is throttled to one line a minute per
  scope. It is a cardinality signal, not a volume one; the exact count stays
  `egress_evicted_total{scope}`. Where it is sustained, `websocket.egress.maxKeys`
  sizes the ledger past the live cardinality (default 4096 keys per scope,
  rounded up to the next power of two).
- `detectGrowth` from `svelte-adapter-uws/sim` reports `rSquared` alongside the
  slope, and accepts `minRSquared` as a fourth vote. No action: the option
  defaults to 0, so every existing verdict is unchanged, and the new field is
  additive on a returned report. Set it (0.5 is the value the bundled leak lane
  uses) when trending a noisy real-world series such as resident set size,
  where a least-squares line eventually tilts through any long enough window.
- `svelte-adapter-uws/observability` publishes the versioned telemetry contract;
  generated operator docs, dashboard, queries, rules, and runbook ship with it.
- Transport counters and histograms cover HTTP completion, upgrade decisions,
  inbound WebSocket work, connection lifetime, and native publish outcomes.
- `platform.pressure.sampledAt` (also on `platform.introspect().pressure`)
  separates a reading from the startup placeholder: `null` until the first
  sampler fold, the wall-clock stamp of the most recent one afterwards. In 0.5
  the snapshot's fields were zero-initialised with nothing in the shape to say
  they had never been measured, so anything reading it before the first tick -
  most visibly an operator dashboard - showed `0 MB` resident memory as a
  reading. No migration is required; code that already treats `memoryMB === 0`
  as "not sampled yet" can drop that heuristic and branch on `sampledAt`, which
  also covers the fields whose zero is legitimate. It stays `null` for the
  process lifetime under the Vite dev plugin and `createTestServer`, neither of
  which runs a sampler.

## Adapter upgrade checklist

1. Read the [ecosystem order](./ecosystem-0.5-to-0.6.md) before changing a
   multi-package deployment.
2. Audit every presence/cursor projection and client presence-update field.
3. Classify every clustered publish lane as volatile or externally ordered.
4. Confirm game traffic has one I/O worker or an external authority.
5. Exercise payload-over-limit and slow-consumer behavior in both dev and prod.
6. Update dashboards for exact drop counters and snapshot completeness.
7. Run the package's normal static, unit, and cross-repository gates before
   promoting the whole compatible tuple.
8. Exercise every WebSocket authenticate-cookie setter and deletion with an
   explicit path under local HTTP and production HTTPS.

## Promotion and rollback

Promote the adapter first, extensions second, and realtime application last,
using the exact packed artifacts named by the ecosystem sequence. Keep the old
lockfile, build artifact, configuration, and any extension-owned storage
snapshot until the candidate has passed reconnect and replay checks under
production-shaped traffic.

If the candidate fails before promotion, leave the stable tuple routed and fix
the prerelease forward. If it fails after deployment, stop writes that depend
on a new extension storage format, restore the snapshot when its owner requires
that step, and restore the complete 0.5 tuple in reverse dependency order:
application/realtime, extensions, adapter plus native addon. An atomic
