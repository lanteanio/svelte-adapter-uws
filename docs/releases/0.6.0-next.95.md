## Consumer changes

### Added: an app-driven topic epoch mint

Changing a topic's seq authority - counter to external allocator, partition to partition, a reset store - left client offsets pointing into a seq space that no longer continues them, with nothing repudiating them; `bumpTopicEpoch(topic)` now mints that topic a fresh generation so those offsets cold-rehydrate at their next resume.

- **Affects:** Apps whose topics change seq authority at runtime; every other topic keeps the process generation exactly as before.
- **Action:** None unless you change an authority - then call it on each worker where the change lands, since app code runs on every worker and the equality-only epoch repudiates old offsets everywhere identically.
- **Requires:** No new dependency or option.
- **Compatibility:** The subscribe ack and resume compares pick the minted value up through the same read authority `topicEpoch` wraps; the override rides the bounded per-topic map the relay-loss mint already uses. `createTestServer` and `vite dev` now answer per-topic epochs through the same shared module.
- **Engineering detail:** [Added for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Added: the send lanes take an explicit gap-fill `seq`

A resume hook replaying history had no way to put per-frame sequence numbers on what it sent; `options.seq` on `send` and `sendWire` now stamps the envelope and the binary frame's seq slot identically, side-effect-free - no counter advances, nothing recorded or captured.

- **Affects:** Resume hooks and replay backends doing gap-fill through the send lanes; every existing call is byte-identical without the option.
- **Action:** None to keep current behavior. Gap-fill replay passes each frame's stored seq: `platform.send(ws, topic, event, data, { seq })`.
- **Requires:** No new dependency or option.
- **Compatibility:** Number and bigint take the publish lanes' validation and safe-integer range; `false`/`null`/absent mean no seq; `true` throws, since the send lanes have no counter to draw. `sendWireBatch` deliberately takes no seq option - one value cannot be one-seq-per-entry; replay discrete frames through `sendWire`.
- **Engineering detail:** [Added for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Added: the static lane answers the full RFC 9110 precondition set

Mutable assets now serve `Last-Modified` beside the `ETag` and honor `If-Match` and `If-Unmodified-Since` with 412, `If-Modified-Since` with 304, and the list and `*` forms of both entity headers, evaluated in the RFC's order so a failed `If-Match` is never converted into a 304.

- **Affects:** Caches and clients revalidating static and prerendered responses; a cache that lost the ETag can now revalidate by date instead of re-downloading every full body.
- **Action:** None. Versioned immutable assets are unchanged - their filename is the validator and they carry neither header.
- **Requires:** No new dependency or option.
- **Compatibility:** Every request that answered 304 before still does; the new answers only add 304s and 412s where the RFC requires them. `If-Match` compares by opaque equality against any validator the lane issued, because every validator is weak by construction and strict strong comparison would refuse the exact tag the server handed out. `last-modified` joins the reserved `staticHeaders` keys, since the date preconditions answer from the file's real time.
- **Engineering detail:** [Added for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Added: a displaced subscription-accounting sink now says so

The counter lives in one `globalThis` slot, so a second copy of the runtime in one worker silently takes every delta - freezing one total while the other is charged releases it never matched; installing over a different sink is now `ADAPTER-ERR-SUBSCRIPTION-SINK-DISPLACED`.

- **Affects:** Deployments or suites where two copies of the adapter runtime load in one worker - a duplicated dependency instance, or two built fixtures imported by one test process. A single copy never reaches it.
- **Action:** None unless it fires; then deduplicate the runtime instance rather than the counter, which is a symptom.
- **Requires:** No new dependency or option.
- **Compatibility:** Clearing the slot to `null` and reinstalling the same function are not displacements, so releasing the slot stays ordinary. This names the topology; it does not change how subscriptions are counted.
- **Engineering detail:** [Added for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Added: the control/ack channel is bounded per connection

It amplifies - a client names a topic in a few bytes and is answered with a whole frame - so a connection may now be sent 4 MiB of protocol frames per 10-second window, and one that exceeds it is closed with 4429 rather than served.

- **Affects:** Every deployment. Measured at the worst legal shape, one 8 KB `subscribe-batch` is answered with about 97 KB across 1,345 frames, and nothing rate-limited the repetition: every `messageAdmission` ceiling is disabled unless configured.
- **Action:** None. A reconnecting client restoring 256 topics spends about 15 KB of the window and a 5,000-topic restore about 300 KB, so a healthy burst is orders of magnitude clear of it.
- **Requires:** No new dependency or option. The ceiling is fixed rather than configurable.
- **Compatibility:** Only frames the adapter emits in answer to a client are charged - acks, denials on both the JSON and the binary game lane, `wire-id` announces, protocol errors, `welcome`, `lease-ok`, window grants - measured in UTF-8 bytes on the wire. Application `send` and `publish` are never charged here and the tenant egress budgets are unchanged. The close is 4429, which the bundled client already classes as throttling and reconnects on; nothing new goes on the wire, because the protocol is frozen at revision 1, and the operator is told through `ADAPTER-ERR-CONTROL-EGRESS-EXHAUSTED`, carrying the connection's request id, instead.
- **Engineering detail:** [Added for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Changed: a subscription-drift report now says how many connections it summed and how many a close had already settled

A membership counted twice and a closed connection still in the live set produce the same sum, so the two quantities that separate them now ride on the report instead of being reconstructed by whoever reads it.

- **Affects:** Anyone reading `subs.total-mismatch` diagnostics; the two existing fields are unchanged and two more are added beside them.
- **Action:** None. A reader keying on `totalSubscriptions` and `summed` keeps working.
- **Requires:** No new dependency or option.
- **Compatibility:** Additive. `connections` is always present on a mismatch; `settled` appears only when the snapshot could answer, so an absent field means unmeasured rather than zero.
- **Engineering detail:** [Changed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Changed: the `seq` publish option speaks one table, and refuses what it cannot carry

A value outside the contract - a numeric string, an object - now throws naming the legal forms instead of silently drawing the local counter, and an integer past the wire's safe-integer range throws instead of rounding; `{ seq: null }` means no seq, and `bigint` joins `number`.

- **Affects:** Callers passing seq values outside `boolean | number` - a numeric string from a JSON column was the typical accident - and, separately, callers passing an integer above `Number.MAX_SAFE_INTEGER`, such as a snowflake or a large Kafka offset, which previously published as a rounded value. Also `publishWireBatch` entries, where `true`, `false`, and `null` now act per entry as overrides of the shared options instead of falling through silently.
- **Action:** Pass a number or bigint for an explicit authority's value, `false` or `null` for no seq, `true` or nothing for the counter. A caller that relied on a non-contract value drawing the counter should say `true`. An authority whose ids run above the safe-integer range needs the wide id moved into the event data, or offset by a per-topic base, since `seq` now refuses it rather than rounding it.
- **Requires:** No new dependency or option.
- **Compatibility:** Absent, `true`, `false`, and in-range numbers behave exactly as before, on every lane and every surface (production, `createTestServer`, `vite dev`). `null` moves from counter to no-seq; non-contract values move from counter to `TypeError`. Two breaks to know about: an integer above `Number.MAX_SAFE_INTEGER` moves from a silently rounded publish to a `TypeError`, because the double seq space stops having a neighbour at distance one there and adjacent ids collapse onto one value, which stalls a client watermark that only advances on a strict greater-than.
- **Engineering detail:** [Changed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Changed: four metric help strings describe what is counted rather than which layer counted it

`# HELP` named a native C++ fan-out and a native backpressure limit; those are implementation details, and a help string an operator reads to interpret a number should not require knowing which runtime produced it.

- **Affects:** Anyone reading `# HELP` on the metrics endpoint for `ws_publishes_total`, `ws_publish_outcomes_total`, `ws_dropped_frames_total` or `ws_dropped_bytes_total`. No metric name, type, label or value changes.
- **Action:** None. A dashboard or alert keying on names and labels is unaffected; only the description text differs.
- **Requires:** No new dependency or option.
- **Compatibility:** Text only, and the meanings are unchanged - "never per-recipient deliveries" and "dropped under backpressure" say the same thing without naming the runtime. The declaration in `src/index.d.ts` keeps this adapter's specifics, and now states one an operator would otherwise meet on a dashboard: a publish that excludes a socket is delivered by a per-socket walk rather than one native call, so it is counted by `ws_publishes_total` and absent from the outcome breakdown - the two do not sum.
- **Engineering detail:** [Changed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a `staticHeaders` value carrying a newline is refused at build time

A CR, LF or NUL in a configured value reached `res.writeHeader` verbatim, where it ends the header field and starts whatever follows - header injection, or a second response; names are now held to the RFC 9110 token grammar too.

- **Affects:** Builds configuring `staticHeaders`. A value or name that could split a response now fails the build instead of shipping.
- **Action:** None for a valid configuration. A build that starts failing was emitting a header a client could not have read correctly - remove the control character from the value, or correct a name that is not a bare HTTP token.
- **Requires:** No new dependency or option.
- **Compatibility:** Refused at build rather than sanitised at request time, so an operator is told rather than quietly served something other than what they configured. Every name the token grammar allows still passes, including the punctuation set, and names are lowercased as before.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a respawning worker is no longer quarantined for the relay backlog its boot could not drain

A crashed worker's replacement filled its ring while booting and the age ceiling read that as a stall, respawning it until the restart limit killed the process; the primary now skips a worker in the fan-out until it reports its reader live.

- **Affects:** Multi-worker deployments with the relay ring enabled, under enough relay traffic to fill a booting worker's ring inside its boot time.
- **Action:** None.
- **Requires:** No new dependency or option.
- **Compatibility:** Both ceilings and the `bytes`/`age` quarantine reasons are unchanged; what changed is that a booting worker is no longer handed frames to be judged on. A worker publishing into the relay before its siblings have attached reaches fewer of them, which the receiving worker already treated as a stream joined mid-flight rather than a lost frame.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a recover subscribe without a `ref` is refused loudly instead of dying silently

A subscribe asking for history could hit the saturated gate and get nothing back, leaving the client believing itself subscribed and resuming into a silent gap; it now gets `{"type":"error","code":"RECOVER_REQUIRES_REF"}` up front, on all three server surfaces.

- **Affects:** Hand-rolled clients only; the bundled client stamps a `ref` on every path, including the reconnect resubscribe batch.
- **Action:** Include a `ref` on any subscribe that carries `recover`. A `subscribe-batch` naming history in its recover map needs its one `ref` for the same reason.
- **Requires:** No new dependency or option.
- **Compatibility:** Plain ref-less subscribes keep their documented silence, and `recover` against a server with no resume hook stays ignored - there is no history to miss. The refusal engages only where the recover lane would.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: the cursor plugin stops decoding and parsing frames the runtime already parsed

Its message hook now reads the pre-parsed envelope the adapter hands every hook, which also removes a per-message decoder allocation and a crash on a frame whose whole body is null.

- **Affects:** Every connection on a server with the cursor plugin installed, since that hook inspects each frame before the application's own handler sees it.
- **Action:** None.
- **Requires:** No new dependency or option.
- **Compatibility:** No wire or API change. Binary frames, frames over 8 KiB and anything the adapter did not pre-parse still take the decode path, which now shares one process-wide decoder.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: the consistency auditor no longer reports a subscription drift that never happened

A connection whose native handle was freed while the auditor walked it was skipped from the window but still counted by the cap accountant, so the cross-check compared a complete counter against a short sum and reported a mismatch no membership explained.

- **Affects:** Deployments running the per-worker consistency auditor (`CONSISTENCY_AUDIT_INTERVAL_MS`) on a worker small enough for its whole population to fit one audit window; the rate tracked connection churn, so a busy worker reported more of them.
- **Action:** None. Re-read any `subs.total-mismatch` history against this fix before treating it as evidence.
- **Requires:** No new dependency or option.
- **Compatibility:** No wire, option, or metric name moved. A window that omits any connection now withholds the cap accountant instead of cross-checking against a partial sum, which is what a partial slice already did; a complete window still runs every check.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a batch call's `excludeWs` now excludes on both lanes

`publishWireBatch` honoured a call-level exclusion only for stateless codecs, so opting a codec into batch framing silently dropped it and the author heard its own updates back; the call-level socket now defaults every entry, and a per-entry `excludeWs` overrides it, on either lane.

- **Affects:** Callers passing `excludeWs` on `publishWireBatch`'s options with a stateful codec - previously ignored there without an error.
- **Action:** None. Per-entry exclusions behave exactly as before.
- **Requires:** No new dependency or option.
- **Compatibility:** The batch-level form is now documented on both surfaces; it was honoured undocumented on the stateless lane and ignored on the stateful one. An entry-level `null` exclusion now means absent (inherit the call-level default) on both lanes, where the stateless lane previously read it as an override to nothing.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: the cluster relay's frame ceiling now measures encoded bytes

It compared UTF-16 string length, so a multibyte-heavy frame up to three times the configured size passed the sender and could land over every sibling worker's byte-measured backlog ceiling at once - the mass quarantine the ceiling exists to prevent.

- **Affects:** Multi-worker deployments that set `CLUSTER_RELAY_MAX_FRAME_KB` and relay non-ASCII payloads; ASCII payloads measured identically before and after.
- **Action:** None. A deployment relying on the old undercount to sneak larger multibyte frames through should raise the ceiling to the size it actually intends.
- **Requires:** No new dependency or option.
- **Compatibility:** Strictly tighter: encoded bytes are never fewer than code units, so nothing previously refused is now admitted. Refusal reports carry the exact encoded size.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a `seq` the wire cannot carry is refused even while an egress ceiling is shedding

The publish lanes validated the value as a side effect of stamping, which happens after the ceiling decides, so a bad `seq` came back as an ordinary-looking `false` under load and threw only once traffic dropped.

- **Affects:** Callers passing a `seq` outside the contract while an egress budget is armed. With no budget configured the refusal already arrived immediately and nothing changes.
- **Action:** None. The `TypeError` that now arrives on the offending call was always the correct answer; it was previously deferred to the first quiet window, pointing at a deploy that could be weeks old.
- **Requires:** No new dependency or option.
- **Compatibility:** The refusals, their messages and their classes are unchanged - only their timing is. A refused value charges no egress and advances no counter. `publishWireBatch` now takes the same decision at its call gate, so an empty batch refuses what a full one refuses, on production, `createTestServer` and `vite dev` alike.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a batch that refuses one message's `seq` no longer publishes the ones before it

The atomic pre-pass asked only whether the deployment was clustered, and that question answers accepted without reading the value on a single worker - so `batch()` delivered a prefix and `publishBatched()` spent sequence numbers on frames it never sent.

- **Affects:** Single-worker deployments - the default - calling `batch()` or `publishBatched()` with a `seq` outside the contract on any message but the first. Multi-worker runtimes already refused these at the pre-pass.
- **Action:** None. The same `TypeError` is thrown; what changes is that it arrives before anything has been published or stamped.
- **Requires:** No new dependency or option.
- **Compatibility:** No accepted call behaves differently. A refused `publishBatched` no longer advances the per-topic counter, so a topic's sequence no longer skips values that never reached a client - which is what made this hard to see, since nothing on the wire marks such a gap. `createTestServer` takes the same order on both surfaces.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: the admin route refuses a target that normalizes out of its own prefix

The route matched the raw request target while the `Request` handed to `admin()` had its dot segments resolved, so `GET /__realtime/../reflect` reached the handler describing itself as `/reflect` - a path outside the namespace that handler dispatches and authorizes on.

- **Affects:** Apps exporting an `admin(request)` handler, on the auto-mounted route. Every ordinary target is unaffected, including one that resolves back inside the prefix.
- **Action:** None. An admin handler that assumed `request.url` lay inside its prefix was right to; it now always does.
- **Requires:** No new dependency or option.
- **Compatibility:** Such a target now answers 400 before any body is read, instead of reaching the handler. A percent-encoded `..%2f` is a single opaque segment rather than a dot segment, so it keeps the prefix and is still served. `createTestServer` takes the same decision.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: `protection: 'auto'` was documented as inert without an admission ceiling, and is not

Escalation to `'elevated'` reads the pressure sampler alone, and that sampler runs unconditionally - so an app setting only `protection: 'auto'` does reach elevated, where every refusal widens its `Retry-After` jitter.

- **Affects:** Anyone who read the declaration and concluded `'auto'` did nothing without `upgradeAdmission`. No behaviour changed; the description did.
- **Action:** None, unless the wording drove a configuration choice - `'auto'` without a ceiling is a working configuration that stops at elevated.
- **Requires:** No new dependency or option.
- **Compatibility:** Documentation only. What genuinely needs a ceiling is the auto step INTO `'siege'`, which compares over-capacity rejects against that ceiling's admit rate; a pinned `'elevated'` or `'siege'` needs no ceiling either.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a worker's uncaught exception costs one worker, not the process

A worker thread holds uWS socket handles Node does not track, so tearing the thread down after an uncaught exception closed the libuv loop with a poll handle still active and aborted the process - the supervisor never got to replace anything.

- **Affects:** Clustered deployments (`workers`), where an uncaught exception in a worker could end the whole process instead of one thread. Single-process deployments are unaffected.
- **Action:** None.
- **Requires:** No new dependency or option.
- **Compatibility:** The `cluster.worker-error` event still fires with the same shape, so dashboards and alerts are unchanged; the worker now exits cleanly and is replaced. An application that installs its own `uncaughtException` handler keeps today's behaviour exactly - Node leaves such a worker alive, and the runtime defers whenever it is not the only listener.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: the posture export describes the whole deployment under `workers`

One socket path cannot have several owners, so every worker unlinked the previous one's socket and bound its own: a consumer read one bind-order-chosen thread's posture and believed it was the server's, and any worker's shutdown removed the live socket.

- **Affects:** Deployments setting both `postureExport` and `workers`. Single-process deployments are untouched.
- **Action:** None. The documented path is the same path.
- **Requires:** No new dependency or option.
- **Compatibility:** The primary owns the socket and serves the highest posture any worker is in, carrying that worker's own reason and pressure numbers. The line gains an additive `workers` count of the threads it summarizes; single-process lines do not carry it. The 1 Hz cadence is unchanged; under `workers` its liveness meaning is the PRIMARY's, and a worker that stops reporting keeps its last posture on the line until the heartbeat watchdog terminates it and its exit drops it, about 30 seconds.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: `publishWire` no longer treats an application's options as a relayed frame

The cross-worker relay marked its re-entry with two ordinary option keys, so an app that set them was handled as a sibling worker's relay: it named the topic's seq itself, uncounted, past an armed egress ceiling, and out over the relay.

- **Affects:** Apps calling `platform.publishWire` directly, including through a plugin codec. No documented option changes and no ordinary call behaves differently.
- **Action:** None.
- **Requires:** No new dependency or option.
- **Compatibility:** Those two keys are now inert - a call carrying them publishes as any other origin publish would, drawing the topic counter. In a multi-worker runtime such a call meets the same sequence-authority refusal every other publish meets, which is a `TypeError` where it previously published silently. The batch-admission marker is hardened the same way: an options object that answers for every key no longer gets a publish past a crossed egress ceiling. `createTestServer` and the dev plugin take the same decisions.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: the reserved admin prefix now holds against a target that arrives inside it

The mount matches the raw target while the lanes behind it resolve and percent-decode, so `/foo/../__realtime/introspect` and `/%5f%5frealtime/introspect` both skipped the admin lane and reached the app's own routing inside the reserved namespace.

- **Affects:** Apps exporting an `admin(request)` handler, where the mount is what reserves the prefix. Without one there is no mount, no reservation, and nothing changes.
- **Action:** None. An app that read `/__realtime/*` as a prefix its own routes never see was right to; that now holds for the resolved and the encoded spellings alike.
- **Requires:** No new dependency or option.
- **Compatibility:** Such a target now answers 400 instead of reaching the app, which is the same answer the opposite direction already gives. A dot segment or an escape that lands somewhere ordinary is unaffected - the check is about where a path ends up, so those still resolve and are served normally. The bare prefix stays on the catch-all, exactly as when it is spelled directly. Worth knowing where the reservation is part of a security boundary: a fronting proxy's ACL on the literal prefix sees none of these spellings, so the adapter is what refuses them.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a socket leaves the live set before the rest of its close teardown

The close released the permit, the subscription accounting, the capability counts and the wire states before removing the connection, and none of those is individually guarded - so one throw stranded a socket whose handle was gone in every publish walk and in the auditor's sum, permanently.

- **Affects:** Every deployment, on the connection close path. Nothing about a close that completes changes.
- **Action:** None.
- **Requires:** No new dependency or option.
- **Compatibility:** The removal owes nothing to the releases that followed it, so moving it first changes only what survives a throw among them. A stranded entry read as a ledger mismatch no double charge explained and never cleared, which is the shape that no longer occurs.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a relay frame length with its top bit set no longer wedges the reader

The ring decoded the four-byte prefix with `|`, which yields a signed result, so such a prefix read negative - under the oversized ceiling, under the bytes on hand, and into a parse offset that emitted empty frames until it climbed back to zero.

- **Affects:** Multi-worker deployments with the cluster relay enabled, on a corrupt or hostile length prefix - the input class the ceiling exists for.
- **Action:** None.
- **Requires:** No new dependency or option.
- **Compatibility:** Read unsigned, those same bytes are an enormous frame, which is what they claim to be and what the ceiling already refuses. Every length the ring accepted before is unchanged.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: `If-Range` is evaluated with the strong comparison RFC 9110 requires

Every validator this lane issues is weak by construction, and the range gate took one as a match - so a client could splice a slice onto bytes from a representation that merely shared a validator, and read a corrupt body under a 206 saying it was fine.

- **Affects:** Clients sending `If-Range` with an entity tag against a static or prerendered asset. A plain `Range` is untouched, which is what a resuming download manager sends.
- **Action:** None. A client wanting the range without the consistency claim sends `Range` alone.
- **Requires:** No new dependency or option.
- **Compatibility:** A weak `If-Range` now falls through to the full 200 representation - the fallback a malformed or multi-range header already takes - where it previously answered 206. Since every validator this lane issues is weak, that is every entity-tag `If-Range` it sees; a date `If-Range` is unchanged.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a resume frame's epoch map takes the same grant gate as its sequence numbers

`lastSeenSeqs` had its ungranted topics dropped and `lastSeenEpochs` reached the hook exactly as parsed, so the gate dropped a client-named topic from one hand and returned it with the other - carrying its generation as well as its name.

- **Affects:** Deployments with a resume hook and the wire-subscribe grant gate armed. Both maps arrive on one frame and the hook reads them together, so an ungranted topic was visible through the epoch half.
- **Action:** None.
- **Requires:** No new dependency or option.
- **Compatibility:** Both maps now take one filter, written once so they cannot drift. A granted topic's epoch reaches the hook exactly as before.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: an ephemeral port under reuseport is refused instead of booting a fleet nothing routes to

Every reuseport worker calls `listen()` for itself, so `PORT=0` hands each of them a different port and the single shared port the mode exists to provide never happens - while the balancer, the health check and the startup log all name port 0.

- **Affects:** Linux deployments setting `PORT=0` with reuseport cluster mode. Acceptor mode is untouched and must be: the primary binds once and hands descriptors down, so one ephemeral port is still one port.
- **Action:** Name a real port. Off Linux nothing changes - reuseport is already refused there by its own id, which fires first.
- **Requires:** No new dependency or option.
- **Compatibility:** Refused as `ADAPTER-ERR-CLUSTER-CONFIG-PORT` with the other capacity misconfigurations, before any worker spawns, so the failure is at boot rather than in the routing layer.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a certificate watch that dies after starting no longer takes the process down

Nothing listened for the watcher's `error` event, and an unhandled one is rethrown, so a watch the platform reported as failed after start raised an uncaught exception on a healthy serving process, and on a cluster primary that ends the whole fleet.

- **Affects:** TLS deployments with the certificate watch on, which is the default. A watch that fails to START was always caught; this is the one that fails later, which arrives as an event rather than a throw.
- **Action:** None. If the new line appears, find what stopped the watch - a permission change on the certificate directory, or the platform's watch resources running out - and restart.
- **Requires:** No new dependency or option.
- **Compatibility:** The process now stays up and reports `ADAPTER-ERR-TLS-WATCH-LOST`, or `ADAPTER-ERR-TLS-PRIMARY-WATCH-LOST` on a cluster primary, and enters the same degraded TLS state a watch that never started produces - sticky, so no later success clears it. Its own id rather than the existing watch ids, because the operator's next move differs.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: removing or replacing the certificate directory no longer spins or silently kills the watcher

No platform reports that as an error - Windows narrates the deletion at about a hundred thousand events a second, Linux says one word and goes quiet - so the watcher now checks the directory's identity whenever an event names the directory itself, and ends the watch.

- **Affects:** TLS deployments with the certificate watch on. On Windows a removed directory was a permanent CPU burn, a log line every debounce window and, on a cluster primary, a reload broadcast to every worker on the same cadence; on Linux it was a watch that looked healthy and would never see another renewal.
- **Action:** None. If the line appears, restart the process once the directory is back where the configuration points.
- **Requires:** No new dependency or option.
- **Compatibility:** The watch ends with `ADAPTER-ERR-TLS-WATCH-LOST` (or the primary id) and the same sticky degraded state as any other dead watch; a directory replaced by a new one at the same path is read once more first, so a certificate that arrived with the replacement is served, and on the primary that reload is broadcast. Windows delivers no event for a directory moved aside, so that case stays as before: silent until restart.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).

### Fixed: a custom 101 header named `Connection`, `Upgrade` or `Sec-WebSocket-Accept` is refused instead of written beside the server's own

The upgrade-header check refused unsafe bytes and non-token names but not the names the handshake writes itself, so an application value went out as a second line and a conforming client refused the handshake silently.

- **Affects:** Applications returning `upgradeResponse()` headers named `Connection`, `Upgrade`, `Sec-WebSocket-Accept`, `Sec-WebSocket-Extensions` or `Sec-WebSocket-Protocol`, in any letter case, on the production runtime, `createTestServer` or `vite dev`.
- **Action:** Remove the header; the server writes the first three on every handshake and negotiates the last two from the client's offer. A subprotocol is selected by the client's offer, not by a response header set from the hook.
- **Requires:** No new dependency or option.
- **Compatibility:** Refused the way an unsafe byte is: `upgradeResponse()` throws a `TypeError` naming the header, and a duck-typed result carrying one takes the hook-error path (500, no 101, nothing written). Every other header name is unchanged. Values in the 0x80-0xFF range stay legal and leave as UTF-8 on every surface, which the suites now pin as the one spelling.
- **Engineering detail:** [Fixed for 0.6.0-next.95 in the complete changelog](../../CHANGELOG.md#060-next95---2026-08-26).
